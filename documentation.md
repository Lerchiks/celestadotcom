##  Установка и запуск

Для установки зависимостей выполните из корневой директории проекта:

``` bash
npm i
```

Запуск локального сервера разработки:

``` bash
npm run dev
```

После запуска Next.js выведет локальный адрес приложения в терминал
(обычно `http://localhost:3000`).

### Доступные npm-скрипты

  Команда           Действие
  ----------------- ----------------------------------------
  `npm run dev`     Запуск dev-сервера Next.js
  `npm run build`   Сборка production-версии
  `npm run start`   Запуск production-сервера после сборки
  `npm run lint`    Запуск ESLint

Для production-запуска сначала соберите приложение:

``` bash
npm run build
npm run start
```

##  Архитектура проекта

Проект организован по принципам **Feature-Sliced Design (FSD)**. FSD
помогает разделять код по уровням ответственности и предметным областям,
а также контролировать зависимости между частями приложения.

В исходном описании проекта используются уровни:

``` text
src/
├── app/
├── views/
├── widgets/
├── entities/
└── shared/
```

В классической схеме FSD также предусмотрен уровень **`features`**. Он
предназначен для пользовательских действий и сценариев, которые имеют
самостоятельную бизнес-ценность. В текущем описании структуры `features`
не указан --- его следует добавлять по мере появления соответствующей
логики.

Рекомендуемая целевая структура:

``` text
src/
├── app/       # Инициализация приложения и маршрутизация Next.js
├── views/     # Страницы приложения (проектное название уровня pages)
├── widgets/   # Самостоятельные крупные блоки интерфейса
├── features/  # Пользовательские действия и сценарии
├── entities/  # Бизнес-сущности предметной области
└── shared/    # Переиспользуемая инфраструктура и UI без бизнес-привязки
```

### Правило направления зависимостей

Зависимости между слоями направлены сверху вниз:

``` text
app
 ↓
views
 ↓
widgets
 ↓
features
 ↓
entities
 ↓
shared
```

Верхние уровни могут использовать нижние. Нижние уровни не должны
импортировать код верхних уровней.

Например:

-   `views` может использовать `widgets`, `features`, `entities` и
    `shared`;
-   `widgets` может использовать `features`, `entities` и `shared`;
-   `features` может использовать `entities` и `shared`;
-   `entities` может использовать `shared`;
-   `shared` не зависит от остальных слоёв.

Не следует создавать циклические зависимости между слоями или обходить
архитектурные границы прямыми импортами внутренних файлов соседних
слайсов.

### Слои, слайсы и сегменты

В FSD важно различать три понятия:

-   **Слой (layer)** --- крупный уровень архитектуры: `widgets`,
    `features`, `entities` и т. д.
-   **Слайс (slice)** --- часть слоя, выделенная по предметной области
    или назначению. Например, `event-carousel`, `user`, `auth-by-email`.
-   **Сегмент (segment)** --- папка внутри слайса, выделенная по
    технической ответственности: `ui`, `api`, `model`, `lib` и другие.

Пример:

``` text
src/
└── features/
    └── add-to-favorites/
        ├── api/
        ├── model/
        ├── ui/
        └── index.ts
```

Не каждый слайс обязан содержать все возможные сегменты. Создавайте
только те, которые действительно нужны.

## 4. Описание слоёв

### 4.1. `app` --- приложение и маршрутизация

Путь: `src/app`

В проекте используется **Next.js App Router**. Слой `app` отвечает за
маршруты, корневую конфигурацию приложения и интеграцию страниц с
механизмами Next.js.

В `app` располагаются директории маршрутов. Название директории
определяет сегмент URL, а файл `page.tsx` задаёт страницу маршрута.

Пример:

``` text
src/app/
├── layout.tsx
├── page.tsx
├── explore/
│   └── page.tsx
└── dashboard/
    └── page.tsx
```

В `app` также могут находиться специальные файлы Next.js, например:

-   `layout.tsx` --- общий layout сегмента маршрута;
-   `loading.tsx` --- состояние загрузки;
-   `error.tsx` --- обработка ошибок сегмента;
-   `not-found.tsx` --- страница не найденного маршрута;
-   `page.tsx` --- содержимое маршрута.

Используйте `app` для возможностей маршрутизации и интеграции с Next.js,
а основную композицию конкретной страницы выносите в слой `views`.

Пример `src/app/dashboard/page.tsx`:

``` tsx
import Dashboard from '@/views/dashboard-page';

export default function DashboardPage() {
  return <Dashboard />;
}
```

### 4.2. `views` --- страницы приложения

Путь: `src/views`

`views` --- проектное название слоя, который в классической терминологии
FSD соответствует `pages`. Здесь собирается интерфейс конкретной
страницы из виджетов, фич, сущностей и общих компонентов.

Соглашение проекта: слайсы страниц называются по шаблону:

``` text
<название-страницы>-page
```

Например:

``` text
src/views/
└── dashboard-page/
    ├── ui/
    │   └── Dashboard.tsx
    └── index.ts
```

Пример реализации страницы:

``` tsx
import EventCarousel from '@/widgets/event-carousel';
import TemplateCarousel from '@/widgets/template-carousel';

export default async function Dashboard() {
  const eventsTemplates = await getTemplateEvents();
  const templates = await getTemplates();

  return (
    <div>
      <EventCarousel templates={eventsTemplates} />
      <TemplateCarousel templates={templates} />
    </div>
  );
}
```

Это иллюстративный пример на основе черновика: функции
`getTemplateEvents` и `getTemplates` должны быть определены в проекте и
импортированы из соответствующих модулей.

Страница маршрута в `app` должна оставаться тонкой точкой входа: она
импортирует нужный слайс из `views` и отображает его.

### `widgets` --- крупные блоки интерфейса

Путь: `src/widgets`

`widgets` содержит самостоятельные, достаточно крупные части интерфейса,
которые объединяют несколько компонентов и/или бизнес-сценариев.

Примеры возможных виджетов:

-   карусель событий;
-   карусель шаблонов;
-   шапка приложения;
-   боковая панель;
-   панель управления;
-   крупный информационный блок.

Название слайса обычно отражает назначение блока, например
`event-carousel`.

Пример структуры:

``` text
src/widgets/
└── event-carousel/
    ├── ui/
    │   └── EventCarousel.tsx
    └── index.ts
```

Публичный API слайса экспортируется через `index.ts`:

``` ts
export { default } from './ui/EventCarousel';
```

Использование в других слоях:

``` tsx
import EventCarousel from '@/widgets/event-carousel';
```

Не импортируйте внутренние файлы виджета напрямую из других слоёв.
Добавляйте необходимые экспорты в публичный API слайса.

### `features` --- пользовательские действия и сценарии

Путь: `src/features`

`features` --- недостающий в исходном черновике, но важный слой FSD. В
нём размещается функциональность, которая описывает конкретное действие
пользователя или законченный пользовательский сценарий.

Примеры:

-   добавление товара или элемента в избранное;
-   поиск;
-   фильтрация списка;
-   авторизация через форму;
-   подписка на уведомления;
-   создание или публикация сущности;
-   переключение состояния подписки.

Пример структуры:

``` text
src/features/
└── add-to-favorites/
    ├── api/
    │   └── addToFavorites.ts
    ├── model/
    │   └── useFavorites.ts
    ├── ui/
    │   └── AddToFavoritesButton.tsx
    └── index.ts
```

Публичный API:

``` ts
export { AddToFavoritesButton } from './ui/AddToFavoritesButton';
```

Использование:

``` tsx
import { AddToFavoritesButton } from '@/features/add-to-favorites';
```

**Когда создавать feature:** если компонент реализует отдельное действие
или сценарий, который можно осмысленно назвать глаголом или
пользовательским намерением.

**Когда не создавать feature:** если компонент только отображает данные
или представляет базовый UI-элемент. Такой код обычно относится к
`entities`, `widgets` или `shared` в зависимости от ответственности.

###  `entities` --- бизнес-сущности

Путь: `src/entities`

`entities` содержит сущности предметной области приложения: объекты, с
которыми работает продукт, их типы, данные, отображение и базовые
операции.

Примеры сущностей (конкретный набор определяется предметной областью
проекта):

-   `user`;
-   `event`;
-   `template`;
-   `project`;
-   `organization`.

Пример структуры:

``` text
src/entities/
└── event/
    ├── api/
    ├── model/
    ├── ui/
    │   └── EventCard.tsx
    └── index.ts
```

Сущность может содержать:

-   типы и интерфейсы данных;
-   функции получения или преобразования данных;
-   состояние, относящееся к сущности;
-   UI-компоненты для отображения сущности.

Пример публичного API:

``` ts
export { EventCard } from './ui/EventCard';
export type { Event } from './model/types';
```

Сущность описывает сам объект предметной области. Действия пользователя
над ним, если они представляют отдельный сценарий, следует выносить в
`features`.

### `shared` --- общий переиспользуемый код

Путь: `src/shared`

`shared` содержит код, который не относится к конкретной бизнес-сущности
или пользовательскому сценарию и может использоваться на разных уровнях
приложения.

Примеры:

-   базовые UI-компоненты: кнопки, поля ввода, модальные окна;
-   общие стили и дизайн-токены;
-   шрифты;
-   статические изображения и другие assets;
-   общие утилиты;
-   конфигурация;
-   общие типы;
-   инфраструктурные API-клиенты, если они не привязаны к конкретной
    сущности.

Возможная структура:

``` text
src/shared/
├── api/
├── config/
├── lib/
├── assets/
├── styles/
└── ui/
    ├── button/
    └── input/
```

В исходном черновике `shared` описан как место для общих объектов,
например fonts, styles, assets и buttons. Важно: `shared` --- не папка
для всего кода, который не удалось отнести к другим слоям. Каждый модуль
должен быть действительно общим и не содержать бизнес-логики конкретной
фичи или сущности.

##  Сегменты внутри слайсов

Внутри слайсов можно использовать папки-сегменты. Они группируют файлы
по технической ответственности.

  Сегмент    Назначение
  ---------- --------------------------------------------------
  `ui`       React-компоненты и визуальное представление
  `api`      Запросы к серверу, функции работы с API
  `model`    Типы, состояние, бизнес-логика, хуки и селекторы
  `lib`      Локальные вспомогательные функции слайса
  `config`   Конфигурация слайса
  `assets`   Изображения и другие статические ресурсы слайса

Пример:

``` text
src/features/search/
├── api/
│   └── search.ts
├── model/
│   ├── types.ts
│   └── useSearch.ts
├── ui/
│   └── SearchForm.tsx
├── lib/
│   └── normalizeQuery.ts
└── index.ts
```

Не нужно создавать все эти папки заранее. Структура должна отражать
реальное содержимое слайса.

##Публичный API и импорты

Для взаимодействия слайса с другими частями приложения используйте его
публичный API --- обычно файл `index.ts`.

Пример:

``` text
src/
├── widgets/
│   └── event-carousel/
│       ├── ui/
│       │   └── EventCarousel.tsx
│       └── index.ts
└── views/
    └── dashboard-page/
        └── ui/
            └── Dashboard.tsx
```

`src/widgets/event-carousel/index.ts`:

``` ts
export { default } from './ui/EventCarousel';
```

В `Dashboard.tsx`:

``` tsx
import EventCarousel from '@/widgets/event-carousel';
```

### Основные правила импортов

1.  Импортируйте слайсы через публичный API, а не через их внутреннюю
    структуру.
2.  Не импортируйте код из слоя, который находится выше текущего.
3.  Не связывайте слайсы одного слоя прямыми внутренними импортами. Если
    нескольким слайсам нужен общий код, рассмотрите перенос этого кода
    на нижележащий подходящий слой.
4.  Избегайте циклических зависимостей.
5.  Не превращайте `shared` в место хранения бизнес-логики.

> Алиас `@/` используется в примерах исходного черновика. Его
> фактическая настройка должна подтверждаться конфигурацией TypeScript
> (`tsconfig.json`), которая не входила в предоставленные файлы.

## 7. Как определить, куда положить новый компонент

Используйте следующие ориентиры:

  Вопрос                                                        Подходящий слой
  ------------------------------------------------------------- -----------------
  Это настройка приложения, layout или файл маршрута Next.js?   `app`
  Это композиция конкретной страницы?                           `views`
  Это крупный самостоятельный блок интерфейса?                  `widgets`
  Это действие или пользовательский сценарий?                   `features`
  Это бизнес-объект предметной области?                         `entities`
  Это общий UI или утилита без бизнес-привязки?                 `shared`

Примеры:

-   `Button` без бизнес-смысла → `shared/ui`;
-   `EventCard`, отображающая данные события → `entities/event/ui`;
-   `AddToFavoritesButton`, выполняющая пользовательское действие →
    `features/add-to-favorites/ui`;
-   `EventCarousel`, объединяющая карточки и управление каруселью →
    `widgets/event-carousel`;
-   композиция главной страницы → `views/main-page`;
-   `src/app/page.tsx` → точка входа маршрута Next.js.

Это рекомендации по распределению ответственности. Окончательное решение
зависит от того, какую именно логику содержит компонент.

## Соглашения по разработке

-   Соблюдайте направление зависимостей FSD: от верхних слоёв к нижним.
-   Держите код слайса рядом с его ответственностью.
-   Экспортируйте наружу только то, что действительно нужно другим
    слайсам.
-   Предпочитайте понятные названия, отражающие назначение модуля.
-   Не создавайте отдельный слайс для каждого маленького компонента без
    необходимости.
-   Не помещайте бизнес-логику в `shared`.
-   Используйте TypeScript-типы для контрактов данных и props
    компонентов.
-   Для стилей используйте доступные в проекте Tailwind CSS и Sass,
    следуя принятому в конкретной части приложения подходу.
-   Перед завершением работы проверяйте проект командами `npm run lint`
    и `npm run build`.
